# 04 — 多CLI背靠背審查契約

MUST: 背靠背——orchestrator MUST 以獨立 cwd 呼叫各 CLI，並在全部 reviewer 結束前
不得發布、注入或提供任何一家意見（防錨定，保交叉驗證）。這是流程契約，不宣稱能隔離
會主動掃描整台主機的惡意 CLI；該威脅需要 OS sandbox／獨立容器。
ROLE（建議，可按 CLI 擅長分維度）：擅系統設計→審架構/依賴方向；一個→審驗收可機械性與漏洞；一個→找漏的失敗場景/邊界；一個→查範圍蔓延。GitHub CLI ≠ 審查者（是跑CI/查diff的執行工具）。

## PROMPT-TO-CLI
你是獨立審查者。審查【規格+Plan+接縫契約】，只挑問題不客套。MUST NOT 假設它對；用規格檢驗 Plan。

逐項檢查並輸出：
1. 接口/數據結構一致性：Plan 的接口/Schema 與規格一字不差？有無順手改名/加字段？
2. 依賴方向：有無反向/循環依賴？
3. 假設正確性：哪幾條假設有風險或錯？
4. 範圍邊界：有無偷做規格沒要求的事？
5. 驗收完整性：真可機械檢驗？有無「看似可驗、實則靠閱讀」的漏洞？覆蓋夠？
6. 缺失失敗場景：漏了哪些異常/邊界？
7. 過度工程：簡單場景套了複雜設計？
8. 清單外品質：可讀性/安全/效能——指出「會過驗收清單但仍然爛」的地方（防對清單過度優化）。

## OUTPUT（每問題）
```
[維度] 問題 + 具體位置（文件/條） + 嚴重性(高/中/低) + 建議
```
無問題的維度明確寫「無問題」。MUST NOT 湊數編問題，MUST NOT 客氣略過真問題。

## INPUT
[貼 規格 + Plan + 接縫契約]
